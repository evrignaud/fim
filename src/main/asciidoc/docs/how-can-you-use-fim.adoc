= How can you use Fim

== Download a Fim release

You can download a prebuilt release of Fim from the https://github.com/evrignaud/fim/releases/latest[image:icons/download.png[Download] Latest release] +
Then you have to:

* Untar / Unzip the Fim package
* Add the created directory into your PATH to be able to use the `fim` command

== Run Fim using Docker

If you don't have Java and you don't want to install it (or you don't have the required version of Java), you can run Fim using a Docker image. +
All the environment required to run Fim is inside the Docker image. Just pull the image and run Fim.

[IMPORTANT]
====
The Docker image runs only on Linux
====

=== Using the latest published Docker image

Fim releases are published as Docker images on https://hub.docker.com/r/evrignaud/fim/[Docker Hub]. +
You can use them like this.

==== Retrieve the `fim-docker` script:

[source, bash]
----
$ curl https://raw.githubusercontent.com/evrignaud/fim/master/fim-docker -L -o fim-docker && chmod a+rx fim-docker
----

==== Run it:

This script takes the same arguments as the `fim` one. +
If you don't have the Fim Docker image locally it will pull the image first.

[source, bash]
----
$ ./fim-docker -h
----

If you want to use the latest version of the Fim Docker image you can pull it manually:

[source, bash]
----
$ docker pull evrignaud/fim
----

=== Creating your own Docker Image

[source, bash]
----
$ ./build-docker-image
----

The image builds the Fim distribution itself, so this works on a freshly cloned repository.
You need neither a JDK nor a previous Gradle build on the host, only Docker.

Then you can use the provided `fim-docker` script.

== Build Fim

You can build Fim yourself to try the master version.

[IMPORTANT]
====
Fim comes with versioned prebuilt release. I recommend using them as they are OK to be used. +
If you clone Fim's master, a SNAPSHOT is retrieved and there is no guarantee that this particular build of Fim will work properly.
====

* Get the code
** Download the https://github.com/evrignaud/fim/zipball/master[.zip] or the https://github.com/evrignaud/fim/tarball/master[.tar.gz]
** Or clone it using `https://github.com/evrignaud/fim.git`
* Build it by typing the following command (follow <<how-can-you-use-fim.adoc#_step_by_step_procedure,this procedure>> for more details):

[source, bash]
----
$ ./gradlew build
----

Fim is built with Gradle, through the wrapper committed in the repository.
You do not need to install Gradle: the wrapper downloads the version the project uses on first run.
You do need a JDK 17 or later, as described in <<other-stuff.adoc#_fim_requirements,Fim requirements>>.

* You can run the jar file generated into the `build/libs` directory using
the two script files located in the root directory.

** `fim` for Linux or Mac OS X
** `fim.bat` for Windows

It generates also the distribution files into the `build/distributions` directory.
The `fim-shadow-*` ones carry a single self-contained jar, which is what the Docker image uses.

[source, bash]
----
$ ls -a1 build/distributions/
fim-2.0.0-SNAPSHOT.tar
fim-2.0.0-SNAPSHOT.zip
fim-shadow-2.0.0-SNAPSHOT.tar
fim-shadow-2.0.0-SNAPSHOT.zip
----

=== Step by step procedure

Here are some tips on how you can build Fim easily.

==== Getting a JDK

Fim needs a JDK 17 or later to build. If you do not have one, download it from
https://adoptium.net[Adoptium] or use a package manager.

===== For Linux

[source, bash]
----
$ sudo apt-get install openjdk-17-jdk
----

===== For Mac OS X

First install https://brew.sh[Homebrew] if you don't have it, following the instructions on their site.

Then install a JDK.

[source, bash]
----
$ brew install openjdk@17
----

==== Clone Fim

[source, bash]
----
$ cd
$ mkdir projects
$ cd projects
$ git clone https://github.com/evrignaud/fim.git
$ cd fim
----

==== Build Fim

[source, bash]
------
$ ./gradlew build
------

On Windows, use `gradlew.bat` instead.

This compiles Fim, runs the tests and checks the code style.
To build without running the tests, use `./gradlew assemble`.

==== Now Fim is ready

[source, bash]
------
$ ./fim
------

== Verifying Fim

Every check runs from one command, and the same command is what runs on GitHub for each push and pull
request. Nothing has to be pushed to find out whether it passes.

[source, bash]
----
$ ./gradlew check
----

Fim used to be verified by hosted services: Travis CI for Linux and Mac OS X, AppVeyor for Windows, Coverity
Scan for static analysis, Coveralls for coverage. Those are gone, and what replaced each of them is part of
the build itself rather than an account somewhere:

[cols="1,3"]
|===
| Was | Is now

| Travis CI and AppVeyor building and testing
| `./gradlew check` compiles and runs the tests, on your machine and on GitHub

| Coverity Scan static analysis
| **SpotBugs**, which looks for the same class of defect and runs offline.
  Report at `build/reports/spotbugs/main.html`

| Coveralls coverage
| **JaCoCo**, already part of the build.
  Run `./gradlew jacocoTestReport` for `build/reports/jacoco/test/html/index.html`

| Style checking
| **Checkstyle**, unchanged, using `checkstyle.xml`
|===

SpotBugs reports rather than fails the build. The findings on a codebase this old are a backlog, and a check
that blocks every build until the backlog is empty is a check that gets switched off. Set `ignoreFailures` to
`false` in `build.gradle.kts` once the count reaches zero, to keep it there.

=== Coverage has a floor

`check` fails if coverage drops below what is set in `build.gradle.kts`: 90% of instructions, 82% of branches,
90% of lines. It currently sits a few points above each, which is deliberate. A limit set at the exact
current figure fails on the first commit that adds a line, and one set far below never fails at all.

Raise the limits when the real numbers move up. They are there to stop coverage sliding, not to be a target.

The one class under `com/blackducksoftware` is third-party code copied into the tree, with its own licence and
its own history. It is left out of both the coverage figure and the static analysis, so that neither measures
how well Fim tests somebody else's code.

=== What runs on GitHub

`.github/workflows/quality.yml` runs the same checks on **Linux, Windows and macOS** for every push and pull
request, and publishes three things back to the project:

* the **Quality badge** on the README, from the workflow itself
* the **SpotBugs findings**, under Security, Code scanning, which is where Coverity used to put them
* the **coverage figure**, in the summary of each run

Running on three platforms is not box ticking for a tool like this one. Fim reads file permissions,
modification times and SELinux labels, and it has code paths only one platform ever reaches. Several tests
are marked as not applicable to Windows, and only started actually running when this workflow was added.

The coverage badges under `.github/badges` are redrawn by `release.py` rather than committed by the workflow,
so every commit has a person behind it. Between releases the floor above is what keeps the figure honest.

There is a second workflow, `.github/workflows/release.yml`, which runs when a version tag is pushed. It calls
this one first, so a release is verified by exactly these checks rather than by a separate copy of them that
could drift. See <<how-can-you-use-fim.adoc#_releasing_fim,Releasing Fim>>.

=== The two tiers of tests

`./gradlew check` runs everything except the slow tier, which keeps an ordinary build to about three minutes.

[source, bash]
----
$ ./gradlew test            # everything except the slow tier
$ ./gradlew slowTest        # only the slow tier
$ ./gradlew test slowTest   # all of it
----

The scenarios that drive the command line live in `src/test/java/org/fim/integration`. They call the same
entry point a user reaches, so a test covers the argument parsing, the command lookup, the repository checks
and the exit status alongside the behaviour itself. Each one works in a directory of its own under
`build/test-outputs`, using small files, and answers the confirmation prompts through standard input where a
command asks a question.

The slow tier holds the scenarios that need real file sizes. The quick hash modes read three blocks rather
than the whole file, so on a small file those blocks *are* the whole file and every mode behaves alike: the
difference being relied on only exists on files big enough for the blocks to leave gaps. Those tests write
tens of megabytes and walk the whole lifecycle once per hash mode.

Keeping them behind a tag is what allows them to be thorough. A suite everybody waits for on every build is
one that ends up trimmed; one that is asked for explicitly can afford to be slow. Run it before a release,
and after anything touching the hashers or the State comparison.

=== Verifying before every push

The hosted builds ran after a push. You can get the same safety net before one, by enabling the hook that
comes with the repository:

[source, bash]
----
$ git config core.hooksPath hooks
----

`./gradlew check` then runs on every `git push`, and a failure stops the push. Use `git push --no-verify` to
skip it for one push, or `git config --unset core.hooksPath` to turn it off again.

=== Checking on another operating system

Fim runs on Linux, Mac OS X and Windows, and one machine cannot test all three. The workflow does it for you
once the change is pushed, but if you want an answer before that, you can run the build on Linux in a
container using the same JDK the build targets:

[source, bash]
----
$ docker run --rm -v "$PWD":/fim -w /fim eclipse-temurin:17-jdk ./gradlew check
----

That covers the Linux side from a Windows or Mac host. The third platform is the one you have to leave to the
workflow, or to a machine of that kind.

== Releasing Fim

**Pushing a tag is what releases Fim.** Everything else follows from that:

[source, bash]
----
$ git tag 2.0.0
$ git push origin 2.0.0
----

`.github/workflows/release.yml` picks the tag up and does the publishing. The tag is the only thing that says
which version is being released; it is passed to the build as `-PfimVersion`, so the archives are named after
the tag whether or not `build.gradle.kts` was bumped first. A tag pushed by hand releases correctly.

The workflow, in order:

. Runs the whole of `check` on **Linux, Windows and macOS**, plus the slow tier. A release that has not been
  verified on every supported platform is not published
. Builds the distribution at the tagged version
. Creates the release at `+https://github.com/evrignaud/fim/releases/tag/2.0.0+`, with the four archives, the
  self-contained jar and a `SHA256SUMS.txt` you can check with `sha256sum -c`
. Pushes `evrignaud/fim:2.0.0` and `evrignaud/fim:latest` to Docker Hub
. Renders the documentation and publishes it to `gh-pages`

Re-running the workflow is safe. An existing release has its files replaced rather than causing a failure, so
a step that failed for an unrelated reason can simply be run again.

=== Only one thing needs setting up

Pushing the image needs two repository secrets, under Settings, Secrets and variables, Actions:

[cols="1,3"]
|===
| Secret | What it is

| `DOCKERHUB_USERNAME`
| Your Docker Hub account name

| `DOCKERHUB_TOKEN`
| An access token from Docker Hub, under Account Settings, Personal access tokens. Not your password
|===

Without them the image step says it was skipped and the rest of the release still happens, so nothing fails
over a registry the project may not want to publish to. Everything else uses the token GitHub provides to the
workflow, so there is nothing else to configure.

=== Preparing a release before tagging

`release.py` is what sets the version, commits it and creates the tag. It prepares, the workflow publishes:

[source, bash]
----
$ python release.py 2.0.0
----

. Checks the repository is ready: clean working tree, on the release branch, the tag not already taken
. Sets the version in `build.gradle.kts` and commits it as `:package: Release version 2.0.0`
. Creates the `2.0.0` tag
. Runs a clean build: both test tiers, the style check, the static analysis and the coverage floor
. Redraws the coverage badges the README points at
. Collects the archives into `build/release/2.0.0` with their SHA-256 sums, so you can compare them against
  what the workflow publishes
. Sets the version to the next SNAPSHOT and commits that

Nothing is pushed unless you ask for it. Run it, look at what it produced, then push with `--push`, which is
the point at which the release starts.

The image and the documentation are left to the workflow. `--with-docker` and `--with-docs` still build them
here, for a release done without GitHub or just to check they still build, but they are not part of an
ordinary release: doing them in both places would mean two commits racing to publish `gh-pages`.

=== How the Docker image is built for a release

The image is built from the tag rather than from the working tree:

[source, bash]
----
$ git archive --format=tar 2.0.0 | docker build -t evrignaud/fim:2.0.0 -
----

The build context is the tagged content, streamed straight out of the repository. Building from the working
tree would let anything uncommitted, or left over from an earlier build, end up in a released image, and
checking the tag out first would disturb whatever you were working on. This way the image can hold only what
the tag holds. That is what `release.py --with-docker` does, tagging the result both with the version and as
`latest`.

The workflow reaches the same result differently: it has the tag checked out already, so the working tree
*is* the tagged content and it builds from that directly.

The image needs nothing prepared beforehand: it builds the Fim distribution itself, so a freshly cloned
repository and Docker are enough.

[NOTE]
====
The slides are not published with the documentation. They are meant to be reveal.js decks, and the published
ones are, but the build renders them as flat HTML because the reveal.js backend is not configured. Publishing
what is generated would replace working decks with plain pages, so `slides/` on `gh-pages` is left alone until
that backend is restored. Both the workflow and `release.py` copy only the `docs` subtree for that reason.
====
